# 09 · 数据大屏与学习路径设计

> 版本 v0.2 ｜ 2026-09-23 ｜ 状态：已落地（§2/§3 方案未变；M5 Task 5.1–5.7 全部实现，测试 252 passed。两项验收仍开放：5.5 的真 LLM 抽先修边卡在百炼免费额度，5.6/5.7 的浏览器视觉验收待 :8000 重启后补做，详见 §5 各 Task 记录末尾）
> 关联文档：02 架构（五层与存储策略）、04 API、06 前端规范、07 开发计划（本方案作为 M5）

## 0. 先给结论

两个新增点的性质完全不同，工作量和风险不在一个量级：

| 功能 | 本质 | 数据是否现成 | 主要风险 |
|---|---|---|---|
| **数据大屏** | 纯展示层，读现有数据换一种画法 | 90% 现成 | 深色主题污染现有样式；空库时满屏 0 很难看 |
| **学习路径** | 需要**新增一层数据**（前驱依赖关系） | 不现成，现有图谱没有"先学谁"的语义 | 依赖关系不可信 → 路径是编的，答辩被追问就崩 |

因此本方案的两条主线判断：

1. **大屏做成独立页面 `/screen`，不并入现有五视图 Tab。** 深色大屏与浅色工作台共用一套 CSS 令牌必然互相污染，且大屏需要固定 16:9 栅格 + 等比缩放，与现有 `max-width:1720px` 响应式逻辑冲突。独立入口 = 对现有五个视图零改动、零回归风险。
2. **学习路径以"教材章节骨架"为主干，LLM 只在章内抽前驱边。** 谢希仁第 8 版 9 章的顺序本身就是权威拓扑序，不需要算法猜；把 LLM 的搜索空间从"全图 1300+ 节点两两关系"压到"单章内 20~40 个知识点"，准确率是可接受的量级。

## 1. 现状盘点（写方案前已核对）

**已有可复用能力**

- `/api/stats`：documents / documents_indexed / chunks / entities / relations / sessions 六个计数。
- `/api/graph`：节点带 `type`、`degree`、`sources[{doc_name, chunk_id}]`；边带 `label`（LightRAG 的 `keywords`，自由文本）。
- SQLite 五张表：`documents`（含 `filename`、`chunk_count`、`status`、`created_at`）、`sessions`、`messages`（含 `role`、`created_at`）、`agent_runs`、`agent_steps`（含 `tool_name`、`elapsed_ms`、`status`）。
- 前端 `components/graph-view.js`：已解决力导向"收敛后冻结坐标""标签避碰""缩放点线脱钩"三个坑（见 git 892920e / 813443f），大屏中央主视觉应复用它而不是重写。
- 真实数据量（`data/app.db`）：18 篇文档（13 indexed / 5 failed）、48 会话、114 消息、39 次运行、78 步；工具调用分布 subnet_calculator 27 / course_rag_query 5 / ping_host 3 / dns_lookup 1。**大屏有真数据可画，不需要造 mock 起步。**

**关键缺口（决定学习路径做法）**

- 图谱的边是 LightRAG 自由抽取的 `keywords`，**没有受控的 `prerequisite` 语义**，直接拿它做拓扑排序结果不可信。
- 实体的章节归属**不能依赖节点上的 `file_path`**——`graph_service._resolve_sources()` 的注释已明确"实体聚合可能丢失部分 file_path"，必须用 `chunk_id → kv_store_text_chunks.file_path` 反查。全图反查在 43MB 本地存储上很慢，只能离线做一次物化。
- `main.py` 的 lifespan 里 LightRAG 初始化失败只 warning 不抛错，`/api/graph` 在 `RuntimeError` 时返回空。若大屏所有图都依赖 `/api/graph`，一次 LLM 配置异常 = **整屏空白**。

## 2. 数据大屏

### 2.1 定位与验收标准

导师的诉求明确是"展示好看"。因此优先级排序：**视觉密度 > 数据真实 > 交互深度**。验收标准写成可判定的三条：

1. 1920×1080 投屏（F11 全屏）无横向滚动、无错位、3 米外可读最小字号 ≥ 16px；
2. 打开后 3 秒内所有图有内容，且**任何一张图取不到数据时其余图照常渲染**（不允许整屏白）；
3. 页面自己会动：数字滚动、图表轮播切换、底部跑马灯，演示时不需要人操作。

### 2.2 入口与主题隔离

```
static/
├─ index.html          # 现有工作台，不动
├─ screen.html         # 新增：大屏独立入口，只引 screen.css + echarts + 大屏脚本
└─ assets/
   ├─ css/app.css      # 浅色令牌，不动
   ├─ css/screen.css   # 新增：深色大屏专用，与 app.css 完全隔离
   └─ js/screen/*.js   # 新增：大屏视图，不复用 Store（避免两套生命周期纠缠）
```

- 后端加一条路由：`GET /screen` → 返回 `screen.html`（`FileResponse`）。注意必须注册在 `app.mount("/", StaticFiles(...))` **之前**，与 `lightrag_console.mount_console(app)` 同一约束（main.py:70 已踩过）。
- 工作台侧只在概览页右上角加一个"进入数据大屏 ↗"按钮，`window.open('/screen')`，不改 Tab 数组。

**深色大屏令牌（独立一套，不写进 app.css）**

```css
:root {
  --sc-bg: #050B1A;              /* 深蓝底 */
  --sc-panel: rgba(16,34,64,.55);/* 面板半透明 */
  --sc-line: rgba(64,156,255,.22);
  --sc-text: #DCE9FF; --sc-dim: #6E86AD;
  --sc-cyan: #22D3EE; --sc-blue: #3B82F6; --sc-amber: #FBBF24; --sc-green: #34D399;
}
```
配色只此一套，禁止再引入第五种主色。发光边框用 `box-shadow: 0 0 12px rgba(34,211,238,.25)` + 面板四角切角伪元素实现"科技感"，成本极低、效果最明显。

### 2.3 布局栅格（设计稿 1920×1080）

```
┌──────────────────────────────────────────────────────────────────────┐
│  ◤ 计算机网络课程知识图谱与智能问答系统 · 数据大屏      20:30:15  ◢ │  88px 标题栏
├──────────────┬──────────────────────────────────┬────────────────────┤
│ 核心指标 6 卡 │                                  │  工具调用统计(雷达)  │
│ 文档/实体/    │      中央：知识图谱主视觉          │  220px               │
│ 关系/分块/    │   （力导向 + 自动轮播聚焦          ├────────────────────┤
│ 会话/运行数   │    不同实体类型，每 8s 换一类）     │  章节覆盖度(条形)    │
├──────────────┤                                  │  260px               │
│ 实体类型分布  ├──────────────────────────────────┼────────────────────┤
│ (玫瑰环图)    │  近 14 日问答趋势(面积折线)        │ 高频实体 Top10      │
│ 260px        │  200px                            │ (横向渐变条) 300px  │
├──────────────┴──────────────────────────────────┴────────────────────┤
│  ▸ 实时问答：192.168.10.137/27 属于哪个子网 …   TCP 三次握手 …  (跑马灯) │  56px
└──────────────────────────────────────────────────────────────────────┘
```

- 左右栏各 3 块，中央占 ~46% 宽——**大屏的"好看"80% 来自中央图谱 + 数字卡，其余图表是填充密度用的**，不要本末倒置去堆 12 张小图。
- 适配：外层 `.screen-root` 固定 1920×1080，JS 按 `min(w/1920, h/1080)` 设 `transform: scale()` + `transform-origin: center`。这是大屏标准做法，比响应式栅格省事且永不错位。**不要让 ECharts 参与响应式重排**，scale 后 canvas 会糊，`echarts.init(el, null, {devicePixelRatio: 2})` 兜一下。

### 2.4 数据来源：新增 1 个聚合端点

**只加 `GET /api/screen/overview`，一次返回全部图的数据。** 理由：大屏 8 张图若各自请求，30s 轮询 = 每分钟 16 次请求打 LightRAG，且任意一个失败都可能拖垮渲染；单端点 + 分字段容错最稳。

响应结构与计算来源（**逐字段标注，避免实现时现编**）：

| 字段 | 内容 | 数据来源 | 是否需新代码 |
|---|---|---|---|
| `stats` | 6 个核心数 | 复用 `stats` 逻辑 | 否 |
| `entity_types` | 类型→数量 | `graph_service` 全量 snapshot 按 `_node_type` 聚合 | 是（现有前端聚合受 `limit=500` 截断，数字是假的） |
| `top_entities` | 度数 Top10 | snapshot 度数排序（`get_graph` 已算 degree，抽成函数） | 是（小改） |
| `top_relations` | 关系词 Top10 | 边 `label` 计数 | 是（同上） |
| `chapters` | 章号→{文档数, 分块数, 实体数} | `documents.filename` 正则 `第\s*(\d+)\s*章` + 物化表 | 是 |
| `tools` | 工具→{次数, 平均耗时, 成功率} | `agent_steps` 按 `(run_id, step_no)` 自连接 action ↔ observation 行（tool_name 在 action 行，耗时/状态在 observation 行） | 是（纯 SQL） |
| `trend` | 近 14 日问答条数 | `messages.created_at` 按日 `GROUP BY` | 是（纯 SQL） |
| `runs` | 运行数/步数/中断数 | `agent_runs` | 是（纯 SQL） |
| `feed` | 最近 20 条提问文本 | `messages` where role='user' | 是（纯 SQL） |
| `coverage` | 知识点触达 `{touched, total, rate}` | `knowledge_node`（`chapter IS NOT NULL`）LEFT JOIN `knowledge_touch` 单条 SQL 聚合，见 §3.2 与 Task 5.7 | 是（`repository.touch_coverage()`） |

**容错要求（写进验收）**：`/api/screen/overview` 内部每个字段各自 `try/except`，LightRAG 不可用时 `entity_types/top_*` 返回空数组，SQL 部分照常返回。大屏对空数组渲染"暂无数据"占位，**不整屏降级**。

### 2.5 动效清单（"好看"的具体来源，按性价比排序）

1. 数字卡滚动进场（`requestAnimationFrame` 从 0 递增，800ms，自写 20 行，不引 countup 库）；
2. 中央图谱每 8s 自动切换聚焦的一类实体（复用 `graph-view` 的 `applyFocus`，非交互态自动 roam）；
3. 玫瑰图/条形图 `animationDuration: 1200` + `delay` 逐项递增，形成瀑布入场；
4. 底部跑马灯 CSS `translateX` 无限滚动；
5. 面板四角发光切角（纯 CSS）。

**明确不做**：3D 地图、粒子背景、翻页动画。要么性能炸要么土味重，导师场景负收益。

### 2.6 空库兜底

现在 13 篇已 indexed，够用。但演示机若换环境会空。两道保险：

- 前端 `?demo=1` → 全部字段走 `js/screen/demo.js` 内置样例数据；
- 新增 `scripts/seed_demo_data.py`：往 `app.db` 灌 30 条会话 + 90 条消息 + 若干 agent_steps（时间戳铺到近 14 天），只写 SQLite 不碰 LightRAG，30 秒跑完。**推荐用这条**，因为趋势图和工具图有真形状，被追问时答得上来。

## 3. 学习路径

### 3.1 三种做法的取舍（为什么选 1+2）

| 方案 | 说明 | 判断 |
|---|---|---|
| ① 章节骨架 | 用教材 9 章顺序作为宏观拓扑序，章内再细分层 | **采用为主干**。零幻觉、可解释、答辩问不倒 |
| ② LLM 章内前驱抽取 | 单章知识点列表喂给模型，输出受约束的 DAG 边 | **采用为章内细节**。搜索空间小，准确率可控 |
| ③ LLM 直接口述路径 | "学 C 类地址要先学什么" | **不做数据源**。与图谱脱钩、每次结果不同。仅用于给边写"推荐理由"文案 |

### 3.2 数据模型：新增 3 张表（物化，不直连 LightRAG）

**核心决策：学习路径读自己的物化表，不实时查 LightRAG。** 理由：① 路径需要稳定 ID（LightRAG 重建索引后实体名可能变）；② 章节归属反查太慢（§1 已述）；③ 大屏/路径都不该被 LightRAG 可用性绑架。

```sql
-- 知识点：图谱实体的物化快照，带章节归属与层级
CREATE TABLE IF NOT EXISTS knowledge_node (
  kp_id     TEXT PRIMARY KEY,   -- 'kp_' + 短哈希，与实体名解耦
  name      TEXT NOT NULL,      -- 实体名（展示用，允许重名不同章）
  entity_type TEXT,             -- 协议/设备/层次/地址/算法/概念/其他
  chapter   INTEGER,            -- 1..9，NULL=未识别章节
  section   TEXT,               -- 可选：'4.3' 这样的节号
  description TEXT,
  degree    INTEGER DEFAULT 0,
  doc_id    TEXT,
  source_chunk TEXT,
  built_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_kn_chapter ON knowledge_node(chapter);

-- 前驱边：唯一新增的"智能"数据
CREATE TABLE IF NOT EXISTS prereq_edge (
  source   TEXT NOT NULL,       -- 先学（kp_id）
  target   TEXT NOT NULL,       -- 后学（kp_id）
  chapter  INTEGER NOT NULL,    -- 抽取批次所属章
  reason   TEXT,                -- 一句话依据（LLM 生成，仅展示）
  confidence REAL DEFAULT 0.6,
  status   TEXT DEFAULT 'auto', -- auto | approved | rejected（人工审核位，P1）
  PRIMARY KEY (source, target)
);

-- 触达记录：把"学习行为"变成真数据（本方案串联两个新功能的亮点）
CREATE TABLE IF NOT EXISTS knowledge_touch (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  kp_id      TEXT NOT NULL,
  session_id TEXT,
  run_id     TEXT,
  via        TEXT NOT NULL,     -- rag_hit | agent_tool | path_view
  created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_kt_kp ON knowledge_touch(kp_id);
```

**`knowledge_touch` 为什么值得做**：`course_rag_query` 工具与 RAG 问答的检索结果里本来就带命中的实体/关系（`aquery_context` 返回 context）。在检索返回处埋一行"命中了哪些已知 kp_name"，就得到了真实的"知识点触达"数据。于是：

- 学习路径节点状态 = `未触达 / 已触达(n 次)`，**不是编的掌握度，是真的问过/没问过**；
- 大屏多一张有说服力的图："知识点触达覆盖率 37%（148/400）"；
- 答辩时这是"系统能反映学习行为"的实证，比"我们做了个路径"高一个层次。

成本：一张表 + 两处埋点。**建议 P0 就做**，晚做要回补数据。

### 3.3 构建流水线（离线，一条命令）

```
uv run python -m scripts.build_learning_path [--chapter 4] [--all]
  ① 物化：LightRAG snapshot → knowledge_node（含 chunk_id → file_path 反查得 chapter）
  ② 归章：filename 正则 `第\s*(\d+)\s*章` → chapter 1..9；识别不出的 chapter=NULL 不参与路径
  ③ 章内抽取：每章取度数 Top N（N≤40）知识点 + 描述，喂 LLM 输出 [{source,target,reason}]
  ④ 校验：名称必须在白名单内 → 去自环 → DFS 环检测 → 破环（删 confidence 最低边，记日志）
  ⑤ 跨章边：只允许 chapter 小的指向大的（章号即宏观序），违例直接丢弃
  ⑥ 落库 prereq_edge
```

**硬约束（写进代码，不靠 prompt 祈祷）**：
- LLM 输出用 JSON schema 约束，名称不在本章白名单的边**直接丢弃并计数**，日志打印丢弃率；丢弃率 > 30% 说明 prompt 或知识点选取有问题，人工介入。
- 环检测必须做。拓扑排序遇到环会直接抛错，页面会白。破环策略要落日志，别静默删。
- 幂等：重跑同一章先 `DELETE FROM prereq_edge WHERE chapter=?`。

**规模控制**：9 章 × 40 节点 = 360 个路径节点，边约 500~700。这个量级前端可全量渲染，不需要分页。全图 1300+ 实体中未入选的（度数低的长尾）不进路径——**这是正确的取舍，路径本来就该只覆盖核心知识点，演示时也不用解释为什么图上有 1300 个点**。

### 3.4 路径生成逻辑

两个只读端点，无状态、不存"我的路径"（单机演示无多用户，存了反而要解释谁是"我"）：

```
GET  /api/path?chapter=4          → 该章完整 DAG（节点 + 边 + 触达次数）
GET  /api/path/plan?target=kp_ab12 → 到某目标点的必修链
```

`plan` 算法（≤40 行，纯 Python）：
1. 从 `target` 沿 `prereq_edge` **反向 BFS** 求前驱闭包；
2. 闭包内做拓扑排序，**主排序键 = chapter，次排序键 = 拓扑层**（章号优先保证宏观顺序永远符合教材，LLM 抽错了也不会把第 8 章排到第 2 章前面）；
3. 输出有序序列，每项带 `{kp_id, name, chapter, reason, touch_count}`；
4. 返回 `unreachable` 标记：若 target 无任何前驱，明确说"该知识点无前置依赖，可直接学习"，而不是硬凑一条。

### 3.5 前端展示（并入现有工作台，浅色主题）

- 新增视图 `#/path`，与现有五视图同级：`TABS` 加一项 + `app.component('path-view', ...)` + `index.html` 加一行 `<path-view>` 与一个 `<script>`。资源版本号 `?v=m68` 必须同步 +1（历史上多次因陈旧缓存返工）。
- 布局：顶部章节选择（1~9 章 + 全部）+ 目标知识点搜索框 + "生成学习路径"按钮；主体一张大画布；右侧抽屉复用现有实体详情样式。
- **画布用 `layout:'none'` + 手工坐标，绝不用力导向。** 路径要的是确定的顺序感，力导向每次跑出来坐标不同、演示时会跳。坐标算法：`x = 拓扑层 × 180`，`y = 同层内序号 × 64`，节点用圆角矩形（比圆形放得下中文标签）。
- 提供"环形布局"作为第二模式，复刻讯飞那种观感——**仅在所选章节节点数 ≤ 20 时启用**，超过就禁用该按钮并提示。这是从真实截图得到的教训：环形布局 8 个节点好看，30 个以上必然重叠不可读。
- 节点三态配色：未触达（灰）/ 已触达（emerald 实线）/ 路径中（accent 高亮 + 加粗边）。**语义同时带文字标签，不只靠颜色**（遵守 06 §2）。
- 边上标 `reason`（hover 显示，默认隐藏，避免糊屏）；点节点 → 抽屉列出"必须先学 N 个 / 解锁 M 个"。
