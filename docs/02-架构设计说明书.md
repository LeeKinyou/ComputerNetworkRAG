# 02 · 架构设计说明书

> 版本 v0.1 ｜ 2026-09-08 ｜ 状态：待评审 ｜ 上游文档：[01 需求规格说明书](./01-需求规格说明书.md)

## 1. 设计原则

1. **单进程、零外部服务**：一个 uvicorn 进程同时承载 API 与静态前端；不安装/启动任何数据库、缓存、容器。
2. **库而非平台**：LightRAG 作为 Python 库直接嵌入进程，不使用 RAGFlow/Dify 类独立平台，保证前端与交互完全自主可控。
3. **注册表扩展**：文档解析器、智能体工具、存储实现三类变化点全部走"抽象基类 + 注册表"，新增不改主流程（对应 NFR-MAINT-01）。
4. **过程可观测**：ReAct 每一步都是强类型事件，经 SSE 实时推送并落库，界面可看、历史可回放。
5. **演示稳健优先**：默认绑 127.0.0.1；外部依赖只有 LLM API，所有外部调用带超时与降级提示。

## 2. 架构决策记录（ADR）

### ADR-1：RAG/图谱引擎选 LightRAG，不选 RAGFlow

- **决策**：采用 `lightrag-hku` 作为库嵌入；不引入 RAGFlow。
- **依据**：
  - RAGFlow 是独立平台（自带 React 前端与 MySQL/Redis/MinIO/ES 容器栈），官方要求 CPU≥4 核、内存≥16GB、磁盘≥50GB、Docker，与"单进程、不前后端分离、Windows 笔记本演示"冲突；
  - RAGFlow 知识图谱不支持导出，无法搬到自建展示页；其 Agent 为平台内可视化工作流，自定义工具与推理过程展示受平台约束，且 v0.27 起处于后端语言迁移期；
  - LightRAG 默认存储为进程内 + 本地文件，图谱数据可编程取用，天然支持自建 ECharts 图谱页与自定义 ReAct。
- **代价**：复杂版面 PDF 解析能力弱 → 以 Parser 抽象预留，MVP 只吃 md/txt/docx。

### ADR-2：前后端不分离，FastAPI 同源托管静态页

- **决策**：`static/` 由 FastAPI `StaticFiles` 挂载，浏览器只访问一个端口。
- **依据**：部署只起一个进程、无跨域、无独立前端构建；前端用 Vue3/ECharts 的 CDN 版本，免 npm。
- **代价**：前端工程化弱 → 演示型项目可接受，JS 按页面模块化组织即可。

### ADR-3：不引入外部数据库，知识存储与应用存储分离

- **决策**：
  - 知识数据（实体/关系/向量/文档块）用 LightRAG 默认四件套：`JsonKVStorage`、`NanoVectorDBStorage`、`NetworkXStorage`、`JsonDocStatusStorage`，全部落在 `data/lightrag/`；
  - 应用数据（会话、消息、Agent trace、文档元数据）用 Python 内置 **SQLite**，单文件 `data/app.db`；
  - 仓储层定义 `Repository` 抽象接口，SQLite 为唯一 MVP 实现，未来可加 PostgreSQL 实现。
- **依据**：课程量级数据（≤200 篇、≤2 万实体）默认存储足够；SQLite 是文件而非服务，不违反零外部服务原则；整体迁移=拷贝 `data/`。
- **远期**：LightRAG 侧改 `.env` 即可切 Neo4J/Qdrant；应用侧新增仓储实现即可，二者切换互不影响。

### ADR-4：采用 LangGraph 预构建 ReAct 智能体（create_agent），不自写编排循环

- **决策**：智能体编排使用 **LangChain/LangGraph 1.x**，直接用预构建 `langchain.agents.create_agent`（其前身为 `langgraph.prebuilt.create_react_agent`，1.x 起统一入口为 create_agent，内部即标准 model ⇄ tools ReAct 循环图），不自写 while 循环、也不手工拼 StateGraph。
- **决策背景**：已确认**后期必然需要人工审批节点**（对真实网络操作类工具先审后执行）。HITL 依赖"中断—持久化—同线程恢复"，正是 LangGraph 的原生能力（`interrupt()` / `interrupt_before` + Checkpointer + `Command(resume=...)`）；手写循环要自己补状态快照与恢复，成本与出错面反而更大。
- **预构建而非自绘图的理由**：本项目 ReAct 是单循环，create_agent 传入 model/tools/system_prompt/checkpointer 即可得到完整 Agent（含工具重试、并行工具调用、消息状态管理）；自定义部分只有三处——工具适配器、流式事件映射、审批策略，复杂度可控。
- **步骤可视化不丢**：用 `agent.astream(..., stream_mode=["updates","messages"])` 取框架事件，在 `runner.py` 一处映射为本项目固定的 SSE 事件契约（04 §6.2）：
  - updates 中 model 节点的 AIMessage：文本 → thought，tool_calls → action；
  - updates 中 tools 节点的 ToolMessage → observation（耗时与 structured 由工具适配器封装）；
  - messages 流中 model 节点的消息块 → token；运行结束 → final；
  - 注意 LangChain 1.x 流式中节点名为 `model`（0.x 为 agent），映射以此为准。
- **模型层**：create_agent 的 model 用 `langchain_openai.ChatOpenAI(base_url=..., api_key=...)`，DeepSeek/智谱/Kimi/Ollama 均为 OpenAI 兼容；不绑定特定厂商。
- **持久化分工**：LangGraph Checkpointer 用 `langgraph-checkpoint-sqlite`（本地文件 `data/langgraph.db`，仍是文件不是服务）负责"中断续跑"；自有 SQLite `app.db` 的 agent_runs/agent_steps 继续作为展示/回放读模型，两者职责不同、互不替代。
- **约束与可逆性**：代码统一 1.x 写法，不使用已废弃的 0.x AgentExecutor；编排细节收敛在 `app/agent/builder.py` 与 `runner.py`，对上游只暴露 SSE 事件契约，API、前端与工具实现不感知底层框架。

### ADR-5：流式通道选 SSE，不选 WebSocket

- **决策**：RAG 回答与 Agent 步骤均用 SSE（`sse-starlette` + 浏览器原生 EventSource）。
- **依据**：场景为服务端单向推送，SSE 自动重连、实现简单、HTTP 穿透性好；无需双向通道。

### ADR-6：前端免构建（CDN），视觉走统一设计令牌

- **决策**：Vue 3 全局构建版 + ECharts 通过 CDN 引入；样式用一套 CSS 变量（见 06 号文档）。
- **依据**：不需要 node 工具链即可运行/修改，符合演示机部署极简原则；CDN 失败时给出静态提示。

## 3. 五层逻辑架构

```
┌──────────────────────────────────────────────────────────────┐

└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ 接入层 app/api（FastAPI Router）                               │

└──────────────────────────────────────────────────────────────┘
                              ↕
┌──────────────────────┬─────────────────────┬───────────────────┐
│ 能力层               │                     │                   │
│ LightRAG 单例        │ ReAct 循环+工具注册表 │ LLM Client        │
│ app/rag              │ app/agent            │ (OpenAI 兼容/httpx)│
```

### 3.1 层间职责约束

- 接入层只做参数校验、鉴权（MVP 无）、序列化与 SSE 封装，不写业务逻辑；
- 服务编排层是唯一允许同时调用多个能力层组件的地方；
- 能力层组件互相不直接依赖（工具需要检索时通过注入 `RAGService`，不 import LightRAG 单例）；
- 存储层不向上泄漏 SQL/文件格式细节。

## 4. 两条核心数据流

### 4.1 入库链路（异步任务）

```
上传文件(API)
  → IngestionService.ingest(doc_id)
    → Parser 注册表按扩展名取 Parser（md/txt/docx 有实现，pdf/pptx 返回未启用）
    → 统一输出 markdown 文本，缓存 data/parsed/{doc_id}.md
    → 清洗（去重复空行、页眉页脚正则、合并断行）
    → LightRAG.ainsert(text)（内部：切块 → LLM 抽实体关系 → 写四件套）
    → Repository 更新 documents 状态 indexed / failed(原因)
  → 前端轮询文档列表或在管理页看到状态变化；图谱/统计下次读取即刷新
```

### 4.2 智能体问答链路（SSE 流式）

```
POST /api/agent/chat
  → AgentService 创建 agent_runs 记录（running），以 run_id 作为 LangGraph thread_id
  → runner 驱动 create_agent 预构建图（astream, stream_mode=["updates","messages"]）：
      step_start → thought → action(工具名+参数)
        （若该工具 requires_approval：interrupt 暂停 → 等 resume 端点恢复）
      → observation(结果+耗时+状态)
      ……循环（recursion_limit 控制上限）…… → token*（最终答案流） → final
  → 每个事件同时做两件事：① SSE 推给前端；② 结构化写入 agent_steps
  → 结束更新 agent_runs(success/failed/waiting_approval)
```

RAG 问答链路为其子集：`RAGService` 直接调 `LightRAG.aquery(question, mode)`，最终生成阶段按 token 发 SSE，并附 sources。

## 8. 进程与部署视图

- **开发态**：`uv run python main.py`（内部 uvicorn.run，reload 可选）；
- **演示态**：同上，双击启动脚本 `run.bat`（08 号文档提供）后浏览器访问 `http://127.0.0.1:8000`；
- 进程清单：仅 1 个 python 进程（线程/协程在其内部）；任务管理器验证项之一（需求 6.8）。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 演示现场网络不稳/API 故障 | 无法问答 | 统一错误事件与界面提示；配置预留本地 Ollama 基址切换位；课前健康检查 |
| LLM 抽实体噪声大、图谱杂乱 | 展示效果差 | 用计算机网络领域抽取 prompt（限定实体类型白名单）；图谱页支持类型筛选隐藏噪声 |
| docx 样式复杂导致文本顺序错乱 | 入库质量 | python-docx 按段落/表格顺序抽取并保留标题层级；异常文档标记 failed 不阻塞其他文档 |
| 课程材料后续给 PDF/PPT | 需求外扩 | Parser 注册表已留位，按 P1 顺序补实现即可 |
| Windows 下原始 ICMP 需管理员 | ping 工具不可用 | ping 列 P1，优先 dns/http 探测；必要时用 TCP connect 探测替代 |
| 数据量增长后文件存储变慢 | 响应变慢 | ADR-3 预留切换路径；MVP 规模内不处理 |
| LangGraph/LangChain 版本演进 | 兼容风险 | 锁定 1.x 主版本；框架细节只出现在 builder.py/runner.py，事件映射集中一处，升级影响面可控 |
