## 3. 缺陷清单

### BUG-01（P0，任意文件读取）SPA 回退未限制在静态目录内

- 位置：`backend/app/main.py:98-113`（`spa_fallback`）
- 现象：`candidate = STATIC_DIR / path` 直接拼接并 `FileResponse`，未做路径归一化与目录包含校验。编码点段可绕过前端/客户端的 `..` 归一化。
- 证据：
  - `tests/test_main_http.py::test_static_traversal_is_blocked_over_http`（`/%2e%2e/%2e%2e/pyproject.toml` 返回 200）
  - `tests/test_main_http.py::test_spa_fallback_handler_rejects_paths_outside_static_root`（直接调用返回 `FileResponse` 200）
  - 临时探针实测：`/%2e%2e/%2e%2e/%2e%2e/.env` 返回 200、1957 字节，响应中包含 `APP_SECRET_KEY`、`LLM_API_KEY` 字段。
- 影响：未认证即可读取仓库根 `.env`（模型/密钥）、数据库文件、日志，继续向上可读取磁盘任意可读文件。若部署在公网，属于严重信息泄露。
- 建议：解析后校验 `candidate.resolve().is_relative_to(STATIC_DIR.resolve())`，不满足直接 404；拒绝任何解码后含 `..` 的路径；仅对已知白名单扩展名提供文件服务。

### BUG-02（P1，数据残留）删除文档后分块未级联清理

- 位置：`backend/app/models.py:82`（`Chunk.document_id` 声明 `ondelete="CASCADE"`）、`backend/app/api.py:267-275`、`backend/app/db.py:30-39`
- 现象：默认 SQLite 连接未开启外键约束，ORM 也未配置关系级联，`session.delete(document)` 只删除文档行。
- 证据：`tests/test_api_writes.py::test_delete_uploaded_document_removes_chunks_and_index`；临时文件库探针输出 `PRAGMA foreign_keys = 0`，删除后 `documents = 0, chunks = 2`。
- 影响：分块永久残留；`/api/v2/meta` 的 `counts.chunks` 持续虚高；未来若增加会话/运行删除，同样会留下消息与步骤孤儿行。
- 建议：为 aiosqlite 连接注册 `PRAGMA foreign_keys=ON`；或在删除文档时显式删除其 `Chunk`；另加一次性迁移清理历史孤儿分块。

### BUG-03（P1，语义错误）删除不存在的文档返回 403「预置文档不可删除」

- 位置：`backend/app/api.py:269-271`
- 现象：`document is None or document.id.startswith("doc_seed")` 合并为同一个 403 分支。
- 证据：`tests/test_api_writes.py::test_delete_missing_document_returns_404`（期望 404，实际 403）。
- 影响：客户端无法区分“不存在”和“受保护”，错误提示误导；与项目其他按 id 读取接口的 404 约定不一致。
- 建议：先判空返回 404，再判种子文档返回 403。

### BUG-04（P2，接口契约缺口）文档分块接口对不存在的文档返回 200 空列表

- 位置：`backend/app/api.py:278-295`
- 现象：未查询文档是否存在；`limit` 只声明 `le=100`，没有下界。
- 证据：`tests/test_api_writes.py::test_document_chunks_of_missing_document_returns_404`（实际 200 `{"items": []}`）；同一文档的 `/citations` 接口在文档缺失时返回 404，口径不一致。
- 影响：前端会把“文档已删除/不存在”误判为“文档没有分块”；`limit=-1` 可绕过 100 条上限返回全部分块。
- 建议：补 `session.get(Document, ...)` 判空 404；`limit` 增加 `ge=1`。

### BUG-05（P2，行为与注释不符）`question_ids` 组卷不保持传入顺序

- 位置：`backend/app/api.py:764-782`
- 现象：注释写明“顺序保持传入顺序更符合复习预期”，实际仍按 `Question.sort_order` 排序后截断。
- 证据：`tests/test_api_insights.py::test_questions_do_not_leak_answers_and_respect_question_ids`（传入 `q_dns,q_arp`，返回 `q_arp,q_dns`）。
- 影响：错题重做按题库顺序出题，而非错题本顺序；当传入 id 数大于 `limit` 时，截断的子集也不可控，可能漏掉用户勾选的题。
- 建议：查询后用传入 id 列表重排，再截断；或 SQL 层用 `CASE` 排序。

### BUG-06（P2，检索质量）IP/CIDR 被 jieba 拆碎，与函数契约不符

- 位置：`backend/app/retrieval.py:31-54`
- 现象：`tokenize` 先 `jieba.lcut`，再对每个碎片跑 `TERM_RE.findall`，完整地址已无法还原。
- 证据：`tests/test_retrieval.py::test_tokenize_keeps_ipv4_cidr_whole`；实际输出 `['192.168', '.', '10.137', '/', '27', ...]`，文档字符串承诺“英文/编号保持整体（如 192.168.10.137/27）”。
- 影响：`192.168.10.137/27` 这类课程高频查询在 BM25 信道被拆成数字片段，命中率下降；虽然子网卡片仍由正则计算，但引用质量受影响。
- 建议：先对原始小写文本执行 `TERM_RE.findall` 收进 token 列表，再补充 jieba 分词结果并去重。

## 4. 未形成失败断言的风险观察

以下问题已核对代码，但契约边界不够明确，未写成失败用例，建议一并评估：

1. **上传先整包读入内存再校验大小**：`api.py:245` 先 `await file.read()`，`ingest.py:209` 才比较 `max_bytes`。超大请求可在校验前耗尽内存，建议流式读取/先看 `Content-Length`。
2. **`/api/v2/search` 接收 `course_id` 但完全不使用**（`api.py:51, 362-367`）：当前单课程无影响，多课程时会跨课程召回。
3. **取消与收尾存在竞态**：`cancel_run` 直接写 `cancelled`（`api.py:630-644`），已在运行的图在 `finalize_node` 会再写 `completed`（`agent.py:324-332`），取消结果可能被覆盖。
4. **（已修复）全局未启用外键约束**：本轮已为 SQLite 连接注册 `PRAGMA foreign_keys=ON`，并显式删除文档分块；`chat_sessions → messages/runs` 等声明了 `CASCADE` 的关系现在也真正生效。
5. **无鉴权，`user_key` 由客户端自报**：任意调用方可凭已知 `user_key` 读取他人会话、运行与作答（IDOR）。演示环境可接受，上线前必须加认证。
6. **学情归因按文档标题映射章节**（`api.py:689`）：同名文档会把引用记到错误章节。
7. **错题本次级排序为 `last_wrong_at` 升序**（`api.py:1138`）：同为错题时最早错的排前面，若期望“最近错题优先”则方向相反。
8. **`Run.mode` 默认 `course_qa`，统计时归入 `agent`**（`api.py:714-717`）：展示口径与模式命名不一致。

### 连带修复：外键开启后的插入顺序

开启 SQLite 外键后，同一 `flush` 内没有 ORM relationship 的父子表不保证插入顺序，`Course + Document + Chunk` 同批提交会触发 `FOREIGN KEY constraint failed`。已在生产链路补齐父表 `flush`：

- `app/ingest.py::ingest_document`：`add(document)` 后先 `flush`，再插入 `Chunk`。
- `app/seed.py`：课程先 `flush`，章节+概念再 `flush`，边再 `flush`；每份文档 `add` 后 `flush` 再插分块。
- 测试侧用 `memory_db(foreign_keys=True)` 与 `api_harness(foreign_keys=True)` 覆盖上传、种子、级联三条真实路径；其余旧夹具默认保持无外键，避免无关重排。
