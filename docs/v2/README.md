## 开工顺序

1. 所有人阅读 [总设计](./00-重构总设计.md)、[架构说明](./01-架构设计说明书.md)、[需求与验收](./03-需求规格与验收标准.md)。
2. 共同阅读 [API 契约](./05-API与事件契约.md) 和 [协作分工](./09-三人开发分工与交付计划.md)，先确认 DTO、目录归属和交付顺序。
3. 各自按分工阅读数据、Agent、前端和工程文档，领取第一批任务；不用等所有模块完成才开发页面。
4. M0 交付运行骨架后，按每个里程碑的退出条件联调并更新实现状态。

## 契约优先级与变更

- 产品范围以 00 为准，基础设施和故障恢复以 01 为准，Git 协作以 02 为准；03–09 细化实现，不改变以上边界。
- 04 的字段、05 的路径/字段/状态值是本轮补充的开发约定。M0 由三人评审后固定；变更需同一 PR 更新文档、后端 Schema、生成类型、mock 与测试。
- M0 后，业务字段以迁移和模型为实现事实，HTTP DTO 以 FastAPI 导出的 OpenAPI 为实现事实；文档与实现必须同步，冲突不能由各模块自行猜测。
- 当前全部 M0–M4 均未完成。文档里的路径和命令若标为“计划”就是待交付内容，不代表当前可执行。
- 未指定姓名，暂用 A/B/C 表示责任人；不据此假设新人已有特定技术经验。工期在 M0 后根据实际投入估算，不把任务顺序当成日期承诺。

## 本轮新增决策记录

| 编号 | 开发约定 | 原因 |
| --- | --- | --- |
| D01 | 三人按业务纵向拆分，每人交付对应后端、页面和测试 | 避免前端集中等待后端，减少跨人接力 |
| D02 | 初版账号由管理员或种子命令创建，不提供公开注册；浏览器使用会话 Cookie + CSRF | 缩小身份范围，统一前端认证路径 |
| D03 | JSON 成功体直接返回资源，列表使用 items/next_cursor；失败使用 error 包装 | 前后端采用同一响应形状 |
| D04 | V2 首批上传支持 UTF-8 Markdown/TXT 和可提取文本 PDF；扫描 PDF 明确不支持 | 优先验证可定位文本链路，避免隐含 OCR 工作量 |
| D05 | 首版复习采用“未满分有效报告产生建议，用户接受后 1/3/7 天逐级安排”规则 | 给 C 可实现、可解释的确定性基线，不声称掌握概率 |

若负责人调整 D02/D04/D05，应先更新对应需求和契约，再改任务，不在代码中暗改范围。
