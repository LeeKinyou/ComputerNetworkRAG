# 合作开发规范

适用范围：ComputerNetworkRAG V2 的人工开发、多人协作与 AI 辅助开发。本规范先约定 Git 协作与提交方式，后续随工程落地补充代码风格、自动检查与发布流程。

## 1. 分支约定

| 分支 | 职责 | 规则 |
| --- | --- | --- |
| `v1` | 原版代码与历史归档 | 不承载 V2 开发，不与 V2 直接合并 |
| `v2` | V2 集成主线 | 初始化完成后，通过开发分支合入；保持可检查、可追溯 |
| `codex/<type>/<topic>` | 功能、修复或文档开发 | 从 `v2` 创建，完成后通过 PR 或等效差异审查合入 |

开发分支示例：

```text
codex/feat/database-adapter
codex/feat/redis-streams-worker
codex/fix/grading-idempotency
codex/docs/contributing-guide
```

分支名使用小写英文与连字符，topic 描述具体任务。type 选用 feat、fix、refactor、docs、test、chore 等。用户明确指定的分支名优先，不自行重命名已有协作分支。

`v2` 是与 `v1` 无共同历史的独立分支，禁止为合并旧版而使用 `--allow-unrelated-histories`。复用 V1 算法时按文件或实现迁移，并在提交正文注明来源。当前首次初始化可直接在 `v2` 建立初始提交，之后遵循开发分支流程。

## 2. 提交信息格式

统一采用以下结构：

```text
<type>(<scope>): <subject>

<body，可选>

<footer，可选>
```

- type 必填，使用下表中的小写英文类型。
- scope 可省略；涉及明确模块时填写，使用小写英文及连字符。
- subject 必填，默认使用简洁中文，以动作开头，说明具体变化。
- 标题建议不超过 72 个字符，便于日志浏览；不加句末句号，不使用表情或无意义编号。
- 正文与标题之间留一空行。复杂变更说明问题、解决方式、验证与必要影响，不重复描述 diff。
- footer 记录破坏性变化、关联任务等；没有真实任务编号时不编造。

### 2.1 提交类型

| type | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新增用户或系统能力 | `feat(practice): 支持保存答题草稿` |
| `fix` | 修复已有行为缺陷 | `fix(grading): 避免重复提交生成有效成绩` |
| `refactor` | 重整实现且保持既定外部行为 | `refactor(database): 抽取统一事务管理` |
| `perf` | 有明确依据的性能改进 | `perf(retrieval): 缓存已发布的检索快照` |
| `docs` | 文档与注释变更 | `docs(collaboration): 增加 Git 提交规范` |
| `test` | 新增或调整测试、测试数据 | `test(database): 覆盖两种数据库的唯一约束` |
| `style` | 不改变行为的格式调整 | `style(backend): 统一导入顺序` |
| `build` | 依赖、打包与镜像构建 | `build(backend): 引入数据库驱动依赖` |
| `ci` | 持续集成配置 | `ci(database): 增加双数据库检查矩阵` |
| `chore` | 其他维护事项 | `chore(repo): 忽略本地运行数据` |
| `revert` | 撤销已有提交 | `revert(practice): 撤销实验性题目推荐` |

修复错误格式化逻辑属于 `fix`；单纯格式化代码属于 `style`。不要把所有变更都记为 `chore` 或 `update`。

### 2.2 推荐 scope

| 范围 | scope |
| --- | --- |
| 用户、课程、知识库 | `identity`、`courses`、`knowledge` |
| Agent 与学习 | `agent`、`tutoring`、`practice`、`grading`、`learning` |
| 基础设施 | `database`、`redis`、`jobs`、`storage`、`retrieval`、`llm` |
| 前端、部署与协作 | `frontend`、`deploy`、`repo`、`collaboration` |

scope 按主要影响范围选择，不需要列出所有改动目录。Redis Streams 消息队列的业务投递流程通常使用 `jobs`；Redis 连接或客户端实现使用 `redis`。

### 2.3 正文示例

```text
feat(database): 支持通过环境变量选择业务数据库

根据 DB_BACKEND 创建 SQLite 或 PostgreSQL 引擎，业务层共用事务接口。
连接失败返回明确错误，不自动切换到其他数据库。

验证：完成两种数据库的连接与事务集成检查。
影响：修改数据库配置后需要统一重启 API、worker 和 dispatcher。
```

示例仅说明格式。实际提交必须根据真实实现填写，未执行的验证不能写成已通过。

### 2.4 破坏性变更

改变现有 API、配置名称、任务消息契约、数据兼容性或移除已支持行为时，标题在 scope 后加 `!`，正文提供迁移说明，footer 使用 `BREAKING CHANGE:`。

```text
feat(config)!: 统一数据库选择配置

使用 DB_BACKEND 作为数据库选择入口，并在启动时校验连接配置。

BREAKING CHANGE: 旧的 DATABASE_URL 不再读取，需改为 DB_BACKEND 与对应连接参数。
```

不要仅凭变更行数判断是否破坏兼容。删除一个环境变量也可能需要上述标记。

## 3. 提交范围与拆分

一次提交围绕一个可描述、可审查、尽可能可回退的目标。

- 同一功能必要的实现、迁移、相关测试和使用说明可以一起提交。
- 无关功能、全仓格式化、依赖升级和目录搬移分别提交。
- 不将调试代码、临时注释、实验数据和本地环境修复混入功能提交。
- 提交标题应能回答“这次改变了什么”，避免“更新代码”“修复一些问题”“最终版”“WIP”。
- 开发分支可以暂存中间提交，但合入 `v2` 的结果必须完成相关检查，不包含占位密钥、冲突标记或已知无法运行的必要链路。

数据库迁移与依赖必须可追溯：已在共享环境执行的迁移不原地改写，使用新 revision 修正；依赖清单变化时同步提交对应锁文件。配置字段增删或默认值变化时同步更新 `.env.example` 和相关文档。

## 4. 提交前检查

在项目根目录先检查工作区，再显式选择本次文件：

```powershell
git status --short
git diff
# 将下面路径替换为本次实际文件。
git add -- README.md docs/v2/02-合作开发规范.md
git diff --cached --stat
git diff --cached
git diff --cached --check
git commit -m "docs(collaboration): 增加合作开发与 Git 提交规范"
```

默认不使用 `git add .`，避免混入其他人的改动或本地文件。只修改并暂存自己负责的文件；不通过 reset、checkout、restore 或清理命令覆盖未知来源的工作区变更。

按实际影响完成验证：

| 变更 | 最低检查范围 |
| --- | --- |
| 纯文档 | 文件链接、示例一致性、配置名称、空白与冲突标记 |
| 数据访问与迁移 | SQLite、PostgreSQL 对应行为，以及本次涉及的升级、约束或事务 |
| Redis 消息队列 | 本次涉及的投递、确认、重复消息、重试与恢复 |
| MinIO 存储 | 本次涉及的上传/读取、权限、失败状态与引用一致性 |
| Agent 与评分 | 可控模型的相关行为测试；影响效果时补充固定样本评估 |
| 前端 | 实现后可用的类型/构建检查及相关页面交互 |

不为低影响文档调整新增无意义测试。检查命令以实际仓库工具链为准；尚未建立的 CI、测试和启动脚本不声称已执行。无法执行时在 PR 或交付说明中注明原因及未验证范围。

## 5. 禁止提交的内容

- `.env`、API key、数据库密码、MinIO 服务密钥、Cookie、访问令牌和私钥。
- 真实用户答卷、未脱敏个人信息与包含凭据的日志。
- SQLite 数据库、运行时索引、上传课件、MinIO 数据卷、Redis 持久化文件等运行数据。
- 虚拟环境、依赖安装目录、缓存、构建产物和本地参考目录。

`.env.example` 可以提交，只保留字段、注释、非敏感默认值和明确的占位示例。必要测试样本须脱敏、体积受控且具备使用权限；测试 fixture 不作为真实运行数据混入提交。

如果密钥已进入提交，立即撤销或轮换，再按协作流程处理历史；新增 `.gitignore` 或删除当前文件不会清除历史泄露。

## 6. 同步、审查与合并

1. 开始任务前更新对 `v2` 的了解，明确本次范围、依赖和负责文件。
2. 从已有初始提交的 `v2` 创建开发分支；首次配置远程时由维护者指定仓库和分支，不假定已有 `origin/v2`。
3. 提交前审查暂存差异，推送自己的开发分支，创建 PR 或提供等效完整差异。
4. 合入前同步最新 `v2`。个人未共享分支可 rebase；多人共用分支优先 merge，避免改写他人提交。
5. 解决冲突后检查最终行为，重新执行受冲突影响的相关验证，不机械选择整份 ours/theirs。
6. 默认 squash merge，以符合本文格式的 PR 标题作为最终提交标题；有独立审查价值的迁移/重构序列可保留提交。

PR 说明至少包含：解决的问题、最终行为、验证结果、兼容/配置/迁移影响。纯文档变更可简写。一次 PR 对应一个目标；合并方式不替代必要审查。

不强制推送 `v1`、`v2` 或他人共用分支。个人分支 rebase 后确需更新远程时使用 `--force-with-lease`，并确认没有覆盖协作者工作。

## 7. 回退与 AI 辅助协作

已共享或合入 `v2` 的错误提交优先通过 `git revert` 产生新的回退记录，不通过重写主线历史消除记录。涉及数据库或文件格式时另外提供补偿迁移/恢复方案，不能假定 Git 回退会同步回退数据。

AI 辅助开发遵循相同规范：不得编造测试结果、任务编号、指标或已完成状态；提交说明描述最终变化；用户仅要求编写代码/文档时，不自动执行 Git 提交、推送或合并。用户明确授权相关 Git 操作后，在该范围内执行并报告结果。

本文是协作约定，目前尚未配置 commitlint、Git hooks 或远程分支保护。后续自动化检查应与本规范一致，新增约束时同步更新本文。
